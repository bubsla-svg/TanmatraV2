# BOM adoption — blockers, workarounds, and the assumptions you can veto

Executes the decision to adopt the structured ingredient model
(`dish_bom_components`) throughout — see `PANTS-INTEGRATION-PLAN.md` for why
that model wins. Eight blockers stood between "decided" and "done"; each got
a concrete workaround in this change. Every assumption made is listed at the
end with its veto point.

## The blockers and what was built for each

### 1. No writer, no authoring path

`dish_bom_components` had three production readers and zero writers.

**Workaround:** a permanent authoring pipeline, not a one-off backfill —
`scripts/src/bom-backfill.ts` (plan-then-apply, the M-3 pattern) driven by
`.github/workflows/bom-backfill.yml` (mirrors `menu-catalog-v2.yml`'s auth
path step for step). Recipe changes re-run the same vehicle: edit the sheet
JSON / mapping CSV, plan, review, apply. Convergence is asserted after every
apply.

### 2. Slug divergence, silently generated

`dishSlug` is a bare varchar; the recipes seed invents slugs
(`slugify(name)` + `-x` on collision) for sheet dishes that miss the catalog.

**Workaround:** the plan engine contains **no slugify()**. A sheet dish joins
the catalog through `normNameLikeSeed` — a pinned duplicate of
seed-ops-data's own `normName`, so BOM and recipes can never join
differently — and a dish that does not join is **blocked and reported**.
Proof it works: the one blocked dish on the current sheet is *Ragi Dates
Eggless Brownie*, which the catalog genuinely dropped (`ragi-remove.sql`).

### 3. Slash-compound ingredients ("almond milk / low-fat milk")

A BOM row needs one item; the sheet line offers a choice.

**Workaround:** `normalizeName` takes the FIRST option (the calculator's
existing rule), and the plan **records every such assumption** — dish by
dish, "took X, dropped Y" — so each one is visible at review rather than
silently absorbed. `&`/comma composites ("bell peppers & onion") are harder:
the proposal generator refuses to auto-map them to a single item (that would
under-weigh the dropped component) and routes them to the kitchen.

### 4. The 121 unmatched ingredient names

**Workaround:** `scripts/data/bom-ingredient-map.csv` — a reviewed mapping
in the M-3 mould, generated by `scripts/src/propose-bom-map.ts`. 186 distinct
keys: **106** hand-curated aliases (most "misses" were inventory-side
spellings: PARSELY, SPEGHETTI, GREEN CHILLI, BUTTOM MUSHROOM, DALCHIINI =
cinnamon, capsicum = bell pepper), **10** deliberate no-cost verdicts, **1**
token-scored, **69** honestly routed to the kitchen (composites and genuinely
missing inventory rows: avocado, beetroot, chia seeds, soy sauce, tofu…).
Every row is `proposed` until a human flips it to `accepted`; the apply
refuses anything else, and re-generation preserves accepted rows verbatim.
A redundant product-name column makes silent retargeting impossible: if the
sheet's row for an item_no changes, the mapping fails loudly.

### 5. Serving basis

BOM quantities deplete per sellable unit; the sheet's are per serving size.

**Assumption taken:** 1 recipe = 1 sellable unit. Every planned dish carries
its `servingSize` string in the plan so the kitchen vetoes per dish, not in
the abstract.

### 6. Volume density (tbsp/tsp/cup/pcs)

**Workaround:** quantities normalise to grams **at authoring time** through
the calculator's own tables (`gramsFromQuantityText`): the kitchen's dry/
liquid spoon weights, per-piece weights, unicode fractions, ranges. The
runtime never converts volumes — rows land in the DB already weighed, unit
`g`. A mapped line that still parses to zero grams *blocks* its dish rather
than writing a weightless row.

### 7. Production BOM row count unknown

**Workaround:** the workflow's default (write-nothing) run answers it —
`bom-backfill --report` prints the BOM row count, distinct slugs, unit
vocabulary, zero-quantity rows, **and** `recipes.calories_kcal` coverage
(Phase 0's second question: how far the F-1 macros propagated). One click,
read-only.

### 8. (Found during this work) Reseeding inventory wipes the BOM

`seed-ops-data.ts --apply` deletes all `inventory_items`; the BOM's FK is
`ON DELETE CASCADE`, so every reseed silently destroys every BOM row — and
the four engines return to silent no-ops with no error anywhere.

**Workaround now:** the seed counts BOM rows before deleting and prints a
loud warning naming the recovery step (re-run the BOM workflow with
apply=true). The backfill also re-resolves `item_no → inventory_items.id` at
apply time, so reseed-shifted serial ids can never rot the mapping.
**Better fix available, owner's call:** change the FK to `ON DELETE
RESTRICT` and make the seed upsert instead of truncate — a schema migration
I did not write into this change.

## Also fixed on the way: the fallback COGS path

Two defects in `loadDynamicRecipeCosts`, live today, independent of the BOM:

1. **`parseGrams` was `/(\d+)\s*g/`** — 371 of 667 sheet quantity rows (every
   tbsp, tsp, ml, pcs) read as zero grams → zero cost. 96 of 116 dishes were
   silently under-costed. Now delegates to `gramsFromQuantityText`. The
   recipeCosts golden test still passes — its fixtures are all
   gram-denominated, where old and new agree exactly — and both deliberate
   divergences are documented in the test itself.
2. **No BOM read at all.** Costs now overlay from `dish_bom_components`
   where a complete, fully-priced BOM exists (`src/lib/bomCosts.ts`, pure +
   unit-tested). A dish with an unpriced component is **skipped and logged**,
   never partially summed — partial sums are the exact defect being removed.

Price impact is bounded by the existing control: computed costs feed
*pricing suggestions*; only an operator-approved suggestion reaches
`updatePrice`, with the audit trail of a manual edit.

## Assumptions on file — each with its veto point

| # | assumption | veto point |
|---|---|---|
| 1 | 1 recipe = 1 sellable unit | per-dish `servingSize` in every plan |
| 2 | slash-compounds take the FIRST option | per-line "took/dropped" in every plan |
| 3 | volumes convert by the kitchen's dry/liquid spoon tables | `nutritionCalc.ts` `SPOON_DRY`/`SPOON_LIQUID` |
| 4 | ranges take the low end when a unit follows ("6–8 cloves" → 6) | pinned in `bomPlan.test.ts` with rationale |
| 5 | every alias in the mapping CSV | flip the row's verdict/item_no before accepting |
| 6 | salt/ice/water are no-cost | `no-cost` rows in the CSV |
| 7 | `unit` is always `g` in written rows | `bom-backfill.ts` (single write site) |

## Runbook

```bash
# 1. Review the mapping: edit scripts/data/bom-ingredient-map.csv,
#    flip rows to `accepted` (correcting verdict/item_no where wrong).
# 2. Preview what acceptance yields (no DB needed):
pnpm --filter @workspace/scripts run bom-backfill -- --offline --assume-accepted
# 3. Run the "BOM backfill" workflow (report + plan, writes nothing).
# 4. Read the plan artifact. Run again with apply=true.
# 5. After ANY seed-ops-data --apply: re-run the workflow with apply=true
#    (blocker 8 — the reseed cascades the BOM away).
```
