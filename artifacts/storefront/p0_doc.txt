P0


Tanmatra UX/UI Implementation Plan — P0: Clean-State Reset, Legacy Isolation, and Architecture Baseline
P0 is the prerequisite phase that comes before the Phase 4–13 implementation plan. Its purpose is to establish one authoritative application, one route contract, one design-system boundary, and one deployment path before new UX/UI implementation begins.
The governing principle is:


Do not refactor on top of ambiguity.
First:
identify the authoritative application
→ isolate legacy implementation
→ freeze the approved architecture
→ establish clean build and deployment provenance
→ then begin product implementation

P0 — Clean State, Legacy Quarantine, and Production Baseline
Objective
Create a clean and verifiable starting point for the Tanmatra storefront by:


- Identifying the authoritative customer-facing application
- Separating production code from legacy code
- Preserving reusable business logic without preserving legacy UX
- Establishing canonical routes and layout contracts
- Establishing one design-system source of truth
- Establishing deterministic build and deployment provenance
- Preventing old application code from silently re-entering the new storefront
- Creating a reliable baseline for all later phases
P0 is not a visual redesign phase.
P0 is the architecture and governance phase that makes the redesign possible.

14. Constraint Precedence
P0 must establish the precedence used by all planning and recommendation operations.
Recommended order:


1. Legal and safety restrictions
2. Hard allergens
3. Clinical exclusions
4. Dietary pattern
5. Availability and inventory
6. Delivery capacity
7. Plan rules
8. Customer preferences
9. Soft dislikes
10. Variety preference
11. Recommendation ranking




A lower-level preference may never override a higher-level restriction.
Example


Customer likes paneer
+
customer has a hard dairy exclusion
→ paneer must never appear




Exit criteria
All plan generation, Shuffle, Undo, Change Dish, and recommendation services use the same precedence model.




15. Initial Domain Invariants
P0 should define the invariants later tested in Phase 13A.
Mandatory invariants


1. Hard allergens survive generation, Shuffle, Undo, and Change Dish.
2. Keep prevents Shuffle from replacing a meal.
3. Manual replacement clears plan-level Undo.
4. Plan-defining changes invalidate active quotes.
5. Checkout consumes only a server-owned active quote.
6. Expired quotes cannot create payment attempts.
7. One idempotency key creates at most one logical payment result.
8. Fully sponsored activation avoids unnecessary payment.
9. Entitlements are consumed exactly once.
10. No silent meal substitution occurs.
11. Wearables never automatically mutate scheduled meals.
12. Active subscriptions require a confirmed order or verified sponsor activation.
13. Authentication preserves a validated internal return route.
14. Destructive actions disclose financial consequences.
15. Client cannot author authoritative state.
16. Sensitive health information stays out of general analytics.
17. Relevant delivery or plan changes supersede the quote.
18. Unavailable actions explain why.
19. Checkout asks no plan-configuration questions.
20. Restoration is revalidated against current server state.
Exit criteria
The invariants are documented with owner, service boundary, and planned test level.

Route-to-Stitch Screen Wiring Instructions


Route-to-Stitch Screen Wiring Instructions
Use these instructions alongside the P0 through Phase 13 implementation plan. The purpose is to ensure every Stitch design is connected to a real application route, overlay trigger, wizard transition, recovery condition, or component state—not merely stored as an unused source file or screenshot.




1. Core Wiring Principle
A Stitch screen is not considered implemented merely because:


A component file exists
A route file exists
A screenshot exists
The manifest contains an entry
The component is imported somewhere
A test file mentions the screen




A Stitch screen is wired only when the complete chain exists:


Stitch prompt
→ Manifest entry
→ Canonical route
→ Correct layout
→ Route entry point
→ Render chain
→ Trigger or transition
→ Reachable runtime state
→ Required interaction
→ Evidence




For route screens:


Stitch screen
→ app/**/page.tsx
→ production render




For overlays:


Stitch screen
→ parent route
→ visible user trigger
→ overlay controller
→ dialog/drawer/sheet
→ close and focus restoration




For wizard stages:


Stitch screen
→ canonical wizard route
→ state machine stage
→ transition guard
→ rendered stage




For loading, error, empty, and recovery states:


Stitch screen
→ actual domain condition
→ state transition
→ rendered recovery UI
→ recovery action

→ Goal

→ Preferences




Component state
A meaningful runtime state within a route.
Example:


/checkout

Produced while a real operation remains pending.
Empty state
Produced by valid data with zero applicable records.
Error state
Produced by a failed operation.
Recovery state
Contains an action that restores or safely continues the journey.

11. Wiring Status Model
Every entry should progress through:


declared
→ source-defined
→ render-chain-wired
→ trigger-wired
→ transition-wired
→ locally-reachable
→ container-reachable
→ staging-reachable
→ production-reachable
→ visually-approved
→ accessibility-approved




Recommended status fields


{
"declared": "verified",
"sourceDefinition": "verified",
"renderChain": "verified",
"triggerDefinition": "verified",
"transitionDefinition": "verified",
"localRuntime": "verified",

"accessibilityApproval": "pending"
}

pending
verified
missing
partial
broken
blocked
not-applicable








12. Wiring Defect Classification
Missing source


No implementation definition exists.




Unwired source


Implementation exists but is absent from the render chain.




Missing trigger


Rendered implementation exists but no customer action reaches it.




Broken transition


Trigger exists but target state does not render correctly.




Wrong route


State is reachable only from an unapproved route.




Partial stub


Visual shell renders without required interaction or domain behavior.




Domain-disconnected UI


UI state exists but is driven only by local mock state rather than the correct server lifecycle.




Layout mismatch


Screen renders under the wrong application shell.








13. Wiring Quality Gate
A screen or state passes wiring only when:


[ ] Manifest entry exists

[ ] Source implementation exists

[ ] Trigger exists

[ ] Back/close behavior works
[ ] Loading and error behavior exists where applicable
[ ] Domain service owns authoritative state
[ ] Screenshot is attached
[ ] Trace is attached
[ ] Automated test passes
[ ] Evidence SHA is recorded

Where does the customer enter?
