### Current performance characteristics and known pain points

No profiling data, APM traces, or load-test results exist in the repository, and no
benchmark/metrics harness is wired into CI. **Every finding below is therefore derived from
static analysis of the actual source**, not from measurement. Findings are stated with the
specific code path as evidence; the Validation Plan (§ below) specifies what to measure to
confirm each one in a running environment.

Structural facts that shape the risk profile:
- The dispatch engine carries a **5-minute STAT SLA** — latency on that path is a clinical/ops commitment, not a nicety.
- `chargeMandateScheduler` is the only thing that makes cycle-2+ subscription billing fire — it is on the money path.
- The clinical governance engine sits on the packing-station interlock: its latency and failure modes are patient-safety-relevant.
- The storefront runs as a **continuously-billed Cloud Run service with zero public traffic** (no domain mapped).

### Scope of audit

Full architecture. 12 parallel domain sweeps across: dispatch/concurrency, queue + schedulers,
AI gateway I/O, rate limiting + caching, DB schema, API route query patterns, core business-logic
algorithms, storefront data fetching, storefront rendering/bundle, legacy SPA, clinical governance
engine, and CI/infrastructure cost.

## Optimization Summary

### Overall optimization health assessment

**Mixed, with a clear pattern: the codebase already contains the correct solution for most of its
own problems, applied inconsistently.** This is the single most important framing for whoever
picks up this backlog — the majority of fixes are *adopting an existing in-repo pattern at a site
that missed it*, not inventing new machinery.

Concrete instances of that pattern:
- `makeBatchDishResolver()` exists in `menuResolver.ts` explicitly "to avoid N round-trips", is used correctly in `checkout.ts` and `corporate.ts`, and is **not** used at three loop sites in `subscriptions.ts`.
- `lib/userBrief/cache.ts` is a working two-layer TTL cache with a README; the far hotter, far more static menu catalog has **no cache at all**.
- `index.ts` runs an hourly sweeper for `rateLimitsTable`/`sessionsTable`/idempotency rows with a comment naming the exact bug class; `userBrief`'s own in-process `Map` is not in that sweep.
- `lib/integrations-gemini-ai/src/batch/utils.ts` provides bounded concurrency + backoff via `p-retry`; the gateway's own retry loop has **no delay between attempts** and the bulk CMS tools use a naive `for` loop.
- `storefront.yml` path-filters precisely on the 4 `lib/` packages the storefront actually depends on; `deploy.yml` uses a blanket `lib/**` for all three services.

The good news is that this makes the backlog unusually cheap to execute. The bad news is that
several of these gaps sit on the money path, the STAT-SLA dispatch path, and the clinical safety
path.

### Top 3 highest-impact improvements

1. **`OA-DEEP-1.1` — Bound and de-serialize the Grade-3 adverse-event path.** The most severe
   finding in the audit. On an anaphylaxis-class report, locking the contaminated batch lot and
   telling the patient to call 112 are both queued *behind* an untimed, un-retried, uncaught
   PagerDuty call, and the audit dossier is persisted **last**. A single slow third party
   silently blocks both safety actions; a single throw loses the medico-legal record entirely.
2. **`OA-DEEP-1.2` — Collapse the anomaly baseline from 840 serial queries to ~5.** `buildBaseline`
   loops `for (h = 1; h <= 168; h++) { await sampler(...) }`, `runAnomalyScan` drives that
   sequentially across 5 metrics, and the scheduler fires every 5 minutes. That is up to
   **840 serial DB round-trips per tick, ~241,000 per day**, to recompute a 7-day window in which
   only the last 5 minutes changed.
3. **`OA-QUICK-1.1` — Exempt the Razorpay webhook from the 10 req/min payment limiter.**
   A one-expression change on the money path. `app.use("/api/payments", paymentRateLimit)` is a
   prefix match that also covers `/api/payments/razorpay/webhook`, and the limiter keys on client
   IP — so *every customer's* payment confirmation, arriving from Razorpay's small source-IP pool,
   shares **one 10-req/min bucket**.

### Biggest risk if no changes are made

**Failure modes cluster at exactly the moments the system is under load, and several are silent.**
The dispatch race degrades precisely during order surges; the payment webhook limiter starts
429-ing precisely when volume crosses 10 events/minute; the anomaly scheduler's `running` guard
silently *skips ticks* rather than reporting that the previous scan is still draining — so the
system's own anomaly detection degrades first and quietly under the load it exists to detect.
Meanwhile the unindexed `delivery_events` sequential scan and the uncached menu catalog worsen
monotonically with data and traffic growth, with no alarm attached to either.

## Quick Wins

High impact, low effort. All verified Critical/High. Ordered by ROI.

- [ ] **OA-QUICK-1.1 Exempt the Razorpay webhook from the payment rate limiter**
  - **Category**: Network / Cost (money path)
  - **Severity**: High
  - **Evidence**: `artifacts/api-server/src/app.ts:180` — `app.use("/api/payments", paymentRateLimit)` is a path-prefix match, so it also covers `POST /api/payments/razorpay/webhook` (`routes/payments.ts:709`). `paymentRateLimit = rateLimitMiddleware("payments", 10, 60_000)` (`rateLimitMiddleware.ts:49`), and every check is keyed `` `${scope}:ip:${clientIp}` ``. All Razorpay deliveries for all customers arrive from Razorpay's own small source-IP pool and therefore collapse onto **one shared 10-req/min bucket** — the limit whose own code comment says it exists to "block synthetic order fraud" from browser clients. No exemption exists anywhere in `app.ts`; the `express.raw()` mount at line 131 does not skip the limiter mounted afterwards at line 180.
  - **Fix**: Skip the limiter for the webhook sub-path (diff in § Proposed Code Changes). The endpoint is already authenticated by HMAC signature verification and does not need IP throttling designed for browsers.
  - **Impact**: Removes a hard 10/min ceiling on aggregate payment confirmations. Below that volume: no change. Above it: eliminates 429s, the delayed order confirmations they cause, and the Razorpay retry storm they trigger.
  - **Tradeoffs**: Removes IP-based throttling from one endpoint. Acceptable — HMAC verification is the real gate, and the endpoint is already idempotent via `webhook_inbox`.

- [ ] **OA-QUICK-1.2 Add indexes to `delivery_events` (`order_id`, `rider_id`)**
  - **Category**: DB
  - **Severity**: High
  - **Evidence**: `lib/db/src/schema/deliveryEvents.ts:7-14` declares `orderId` and `riderId` as FK columns with **no second `(table) => [...]` argument at all** — zero indexes. Postgres does not auto-index FK columns. Yet the table is queried by `orderId` on the customer order-tracking timeline (`routes/delivery.ts:36-38`), the support agent (`lib/ai/agents/support.ts:153-155`), refund idempotency checks (`routes/payments.ts:668-676`, `routes/refunds.ts:171-176`), and a **double self-join in raw SQL** (`lib/anomalies.ts:189-212`). It is simultaneously a high-write table — every dispatch state change, refund, and rider-sim tick inserts (`dispatch.ts:616/906/1135`, `queue.ts:173`, `riderSim.ts:143`).
  - **Fix**: `index("idx_delivery_events_order_created").on(table.orderId, table.createdAt)` (matches the `WHERE order_id = ? ORDER BY created_at` shape both readers use) plus `index("idx_delivery_events_rider").on(table.riderId)`.
  - **Impact**: Converts every order-tracking page load, support-agent call, and refund check from a full sequential scan to an index range scan. Effect compounds with table growth — this table only ever grows.
  - **Tradeoffs**: Write amplification on a high-write table, plus index storage. Justified: the read pattern is unconditional on every order lookup, and the composite index also serves the `ORDER BY`.

- [ ] **OA-QUICK-1.3 Index the recurring-billing scheduler predicates**
  - **Category**: DB (money path)
  - **Severity**: High
  - **Evidence**: `subscriptionsTable` is indexed only on `userId` (`lib/db/src/schema/subscriptions.ts:139`) — nothing on `status`. `subscriptionMandatesTable` is indexed only on `subscriptionId` (line 287) — nothing on `status` or `nextChargeAt`. Three schedulers run exactly those predicates on a fixed interval: `chargeMandateScheduler.ts:52-62` (`status='active' AND status='active' AND nextChargeAt <= now`), `preDebitScheduler.ts:58-71` (same join, hourly), `subscriptionAbandonmentScheduler.ts:74-88`.
  - **Fix**: `index("idx_sub_mandates_active_next_charge").on(table.status, table.nextChargeAt)` and `index("idx_subscriptions_status").on(table.status)`.
  - **Impact**: `chargeMandateScheduler` is explicitly the only thing that makes cycle-2+ billing fire. Today every tick sequentially scans and joins both tables regardless of size; as the subscriber base grows this eats into the billing sweep's own timing budget.
  - **Tradeoffs**: None significant — these are precisely the predicate columns of hot, repeatedly-run queries.

- [ ] **OA-QUICK-1.4 Add a GIN index for `menu_items.tags` jsonb containment**
  - **Category**: DB
  - **Severity**: High
  - **Evidence**: `tags: jsonb("tags").$type<string[]>()` (`lib/db/src/schema/menuItems.ts:40`) has no GIN index — the index block (lines 111-125) covers only `category/kitchen`, `isAvailable`, and a check constraint. It is queried with jsonb containment: ``sql`${menuItemsTable.tags} @> ${JSON.stringify([`petpooja:${id}`])}::jsonb` `` in `routes/petpooja.ts:702-710`, `:750-758`, and `lib/petpooja.ts:579` — and crucially **inside a `for (const id of itemID)` loop**, so one POS stock webhook carrying N items issues N full jsonb-containment scans of the whole table.
  - **Fix**: `index("idx_menu_items_tags_gin").using("gin", table.tags)` (drizzle-orm 0.45.2 supports `.using()`). Better long-term: promote this to a real indexed `posItemId` column — the tag is being used as a foreign key to an external POS id.
  - **Impact**: Each per-item webhook lookup goes from an O(table) jsonb scan to a GIN probe, multiplied by N items per webhook, during service hours when Petpooja stock updates are frequent.
  - **Tradeoffs**: GIN costs more on write than btree, but `tags` is written rarely (CMS edits) relative to this read path.

- [ ] **OA-QUICK-1.5 Use the existing batch dish resolver in the subscription loops**
  - **Category**: DB
  - **Severity**: High
  - **Evidence**: Three sites in `artifacts/api-server/src/routes/subscriptions.ts` call the *single*-dish resolver in a loop: (1) `POST /subscriptions/:id/swap` lines 1997-1998, with **no dedup and no cap** (`swapItemsSchema.items` has `.min(1)` but no `.max()`); (2) subscription create, lines 864-867, over a day-plan of up to 28 days × 10 items; (3) `validateMacroCapForSwap` lines 688-691, a *nested* loop — per item per member. Each `resolveDishBySlug` call invokes `getMergedCatalog()`, which issues **two** DB reads every time. `makeBatchDishResolver()` exists in the same file's dependency (`menuResolver.ts:196-200`) explicitly "to avoid N round-trips" and is already used correctly at `subscriptions.ts:2640`, `checkout.ts:130`, and `corporate.ts:635`.
  - **Fix**: Build one `makeBatchDishResolver()` per request; replace each in-loop `await resolveDishBySlug(item.slug)` with `resolver.bySlug(item.slug)`. Thread the resolver into `validateMacroCapForSwap` as a parameter rather than letting it resolve internally. Add a `.max()` to `swapItemsSchema.items` while you are there.
  - **Impact**: ~2N round-trips → 2 for an N-item swap. 90%+ reduction on a typical 5-10 item cart; far larger on a 280-item day-plan create.
  - **Tradeoffs**: None — this is adopting the in-repo pattern the file already uses elsewhere.

- [ ] **OA-QUICK-1.6 Collapse the `GET /sales/accounts` N+1**
  - **Category**: DB
  - **Severity**: High
  - **Evidence**: `listAllAccountsWithHealth()` (`artifacts/api-server/src/lib/b2b/accountHealth.ts:247-272`), called by `GET /sales/accounts` (`routes/b2bPlanner.ts:337-344`) with no pagination: `db.select().from(companiesTable)` (no `WHERE`, no `LIMIT`) followed by `Promise.all(companies.map(async (c) => ({ ..., health: await getLatestHealth(c.id) })))`. `getLatestHealth` is its own `SELECT … ORDER BY snapshot_date DESC LIMIT 1` per company.
  - **Fix**: One `SELECT DISTINCT ON (company_id) … ORDER BY company_id, snapshot_date DESC` (or a `LATERAL` join against `companiesTable`). Add a limit/pagination to the company scan.
  - **Impact**: O(N) round-trips → O(1). At 100 companies, 101 queries collapse to 1 on every sales-console load.
  - **Tradeoffs**: None. Note `Promise.all` means these fire concurrently, so this is a connection-pool-pressure and total-query-cost win rather than a pure latency win.

- [ ] **OA-QUICK-1.7 Give order-pipeline jobs a deterministic `jobId`**
  - **Category**: Concurrency
  - **Severity**: High
  - **Evidence**: `scheduleOrderAdvance()` (`artifacts/api-server/src/lib/queue.ts:260-282`) calls ``queue.add(`advance-${orderId}-${step}`, …)`` — in BullMQ the first argument is only a **display name**; dedup is controlled exclusively by `opts.jobId`, which never appears in `queue.ts`. The same `(orderId, step)` pair is reachable twice: `POST /delivery/schedule-advance` (`routes/delivery.ts:126`, an ops endpoint an operator retry can re-hit) and `dispatchRoutedFulfillment()` (`lib/wmsRoutingEngine.ts:105`). `orderPipelineProcessor` unconditionally inserts into `deliveryEventsTable` on every run, and that table has no unique constraint on `(order_id, event)` — so a duplicate job writes a duplicate event row and re-fires `emitDeliveryEvent`, pushing a **second "order delivered" notification to the customer**.
  - **Fix**: Pass ``jobId: `advance-${orderId}-${step}` `` (the string is already being built). Add `onConflictDoNothing` or a unique index on `(order_id, event)` as a second layer for jobs landing after the first completed and was removed by `removeOnComplete`.
  - **Impact**: Eliminates duplicate `delivery_events` rows and duplicate customer-facing push notifications on any retry or re-trigger.
  - **Tradeoffs**: A fixed `jobId` means a legitimate operator-driven re-run of the same `(orderId, step)` while the job is still waiting/delayed/active is rejected. Document this on the ops route, or suffix deliberately-repeated runs.

- [ ] **OA-QUICK-1.8 Lazy-load `CartDrawer` out of the global chrome bundle**
  - **Category**: Bundle size
  - **Severity**: High
  - **Evidence**: `app/layout.tsx:32,208` mounts `<MiniCartBar />` unconditionally on **every route**. `MiniCartBar.tsx:14` statically imports `CartDrawer` and always renders `<CartDrawer open={drawerOpen} … />` at line 58 with `drawerOpen` defaulting to `false` — rendered closed, but bundled regardless. `CartDrawer` pulls in `components/ui/drawer.tsx`, which wraps **`vaul`** — a full drag-physics + portal + focus-management library, per that file's own comment — plus `CartUpsellRail`. All of it ships in the baseline JS for `/about`, `/faq`, `/legal/*`, and the landing page.
  - **Fix**: `next/dynamic(() => import("@/components/cart/CartDrawer"), { ssr: false })`, loaded when `drawerOpen` first becomes true (or when the cart first becomes non-empty).
  - **Impact**: Removes a drag-physics library and the cart/upsell tree from every route's initial bundle. Directly serves the project's own budget in `.claude/rules/ecc/web/performance.md` (<150 kB landing, <300 kB app page, gzipped).
  - **Tradeoffs**: A small load delay on first drawer open. Mitigate by prefetching on cart-add rather than on first click.

- [ ] **OA-QUICK-1.9 Hoist the allergen `Set` out of the inner loop**
  - **Category**: Algorithm (clinical safety path)
  - **Severity**: High
  - **Evidence**: `AllergenTraceabilityService.validateOrderAgainstHiddenMetadata` (`artifacts/clinical-governance-engine/src/AllergenTraceabilityService.ts:97-105`) nests `for (const lot of ingredientLots) { for (const allergy of patientAllergies) { … lot.hidden_carrier_allergens.map(a => a.toUpperCase()).includes(normAllergy) … } }`. The `.map()` allocates a **fresh array** and `.includes()` does a linear scan on **every `(lot, allergy)` pair**.
  - **Fix**: Build `const hiddenSet = new Set(lot.hidden_carrier_allergens.map(a => a.toUpperCase()))` once per lot, outside the allergy loop; then `hiddenSet.has(normAllergy)`.
  - **Impact**: Removes O(lots × allergies) redundant allocations and linear scans from the kitchen packing/traceability path, cutting GC churn proportional to allergy-list × lot-count.
  - **Tradeoffs**: None. Behaviour-identical; add a test asserting a known hidden-carrier breach still trips.

## Deeper Optimizations

Architectural or multi-file changes. All verified Critical/High.

- [ ] **OA-DEEP-1.1 Bound and de-serialize the Grade-3 adverse-event path** ⚠️ **CRITICAL — clinical safety**
  - **Category**: Architectural — reliability / external-dependency isolation
  - **Severity**: **Critical**
  - **Evidence**: `artifacts/clinical-governance-engine/src/AdverseEventWebhookController.ts:192-229`. The `GRADE_3_CRITICAL` branch runs strictly sequentially: `await pagerDutyGateway.triggerIncident(…)` (line 193) → `await kitchenErpGateway.lockBatchLot(…)` (line 206) → `await whatsAppGateway.sendTextMessage(…, emergencyReply)` (line 214) → `await dbGateway.saveDossier(dossier)` (line 228, the **only** persistence call, placed **last**). A grep for `timeout|AbortController|retry|backoff|catch` across the entire file returns **zero matches**. No call is bounded, retried, circuit-broken, or wrapped in `try`/`catch`; none run via `Promise.allSettled`. Each is a hard prerequisite for the next.
  - **Fix**: (a) Persist the dossier **first**, so the medico-legal record survives any downstream failure. (b) Run the three notification/action calls via `Promise.allSettled` so PagerDuty cannot gate the batch lock or the patient warning. (c) Bound every gateway call with a timeout plus a small capped retry (exponential backoff + jitter) or a circuit breaker. (d) Record per-action outcome into `actions_triggered` from the settled results rather than optimistically setting `= true` before the call can fail.
  - **Tradeoffs**: Parallelising changes ordering guarantees — confirm with clinical ops that batch-lock and patient-reply have no required sequencing relative to the page. Persisting first means a dossier can exist with all actions `false`; that is strictly better than no record, but downstream consumers must tolerate it. This touches a safety-critical file: pair the change with tests for each gateway failing independently.
  - **Impact**: Removes a single point of failure from the highest-severity path in the system. Today, a slow PagerDuty blocks quarantining a contaminated batch **and** telling a patient to call 112; any throw loses the audit trail entirely.

- [ ] **OA-DEEP-1.2 Collapse the anomaly baseline from ~840 serial queries to ~5** ⚠️ **CRITICAL**
  - **Category**: Algorithmic / DB
  - **Severity**: **Critical**
  - **Evidence**: `artifacts/api-server/src/lib/anomalies.ts:317-338` — `const LOOKBACK_HOURS = 24 * 7;` then `for (let h = 1; h <= LOOKBACK_HOURS; h++) { … samples.push(await sampler(start, end)); }`. Each iteration is a separate awaited DB call. `evaluateMetric()` calls `buildBaseline()` per metric; `runAnomalyScan()` (lines 520-543) iterates all **5** metrics in a sequential `for` loop with no `Promise.all`; `anomalyScheduler.ts:5` defaults `ANOMALY_SCAN_INTERVAL_MS` to **5 minutes**. Worst case per tick: **5 × 168 = 840 serial round-trips**, ≈241,000/day, recomputing a 7-day window in which only the last 5 minutes changed. *(Found independently by two domain sweeps — rated High and Critical respectively; recorded here at the higher rating.)*
  - **Fix**: (a) Replace the 168-iteration loop with **one grouped query per metric** — `GROUP BY date_trunc('hour', created_at)` over the 7-day window — mirroring the `date_trunc('day', …)` pattern already used in `wbr.ts`'s `ordersByDay`. (b) Cache completed hourly buckets: a fully-elapsed hour's value never changes, so only the current partial hour needs recomputation, turning 167 of 168 samples into a lookup. (c) Run the 5 independent `evaluateMetric` calls via `Promise.all`.
  - **Tradeoffs**: The grouped query must reproduce the existing per-bucket semantics exactly, including the `sampleSize > 0` filter and the hour-of-day seasonal weighting at lines 331-334 — write the grouped version against the existing samplers' output as a golden test before switching. Bucket caching adds a small invalidation surface.
  - **Impact**: ~150× fewer round-trips per tick. At even 10-20 ms/query the current path is **8-30+ seconds of blocking work every 5 minutes**, holding a connection throughout. It also removes a silent-degradation mode: the `running` re-entrancy guard *skips* ticks when the prior scan is still draining, so the anomaly detector quietly stops sampling under exactly the load it exists to detect.

- [ ] **OA-DEEP-1.3 Cache the merged menu catalog**
  - **Category**: Caching
  - **Severity**: High
  - **Evidence**: `getMergedCatalog()` (`artifacts/api-server/src/lib/menuResolver.ts:46-161`) has **no memoization** and is called fresh from `routes/menu.ts:46,57,76` (`/menu/public`, `/menu/alacarte`, `/menu/ranked`), `checkout.ts:130`, multiple sites in `subscriptions.ts`, `teamProfiles.ts:26`, `corporate.ts:635`, `groupOrders.ts:120`, `loyalty.ts:347`, `lib/mealPlanner.ts:54`, and `lib/ai/agents/coach.ts:31`. Every call runs **two** full DB reads: `listMenuItems()` (up to 500 rows) and `getSummariesForSlugs()` — and the latter does `db.select().from(dishReviewSummariesTable)` with **no `WHERE` clause at all**, an unfiltered full-table read, then filters by slug **in JS** (`dishReviews.ts:261-262`). Meanwhile `publicMenuRateLimit` deliberately allows **120 req/min/IP** ("generous for real users"), and there are no `Cache-Control`/ETag headers on any menu route. `lib/userBrief/cache.ts` is a working two-layer TTL cache template for exactly this shape of data, applied to data that changes *more* often than the CMS-driven catalog.
  - **Fix**: (a) Immediate, independent of caching — change `getSummariesForSlugs` to `where(inArray(dishReviewSummariesTable.slug, slugs))`; the full-table read is pure waste. (b) Wrap `getMergedCatalog()` in a short-TTL process cache on the `userBrief/cache.ts` pattern, invalidated from the menu-item write paths (`createMenuItem`/`updateItem`/`setAvailability`/`bulkSetAvailability`/`setImage`/`updatePrice` in `lib/menu.ts`) and the dish-review write paths. (c) Consider `Cache-Control: s-maxage` on `/menu/public` and `/menu/alacarte`.
  - **Tradeoffs**: A cache on the catalog introduces staleness on a surface that carries **price** and the `rdReviewState` patient-safety filter. Keep the TTL short (30-60 s), invalidate explicitly on every write path, and **never** cache the per-profile `/menu/ranked` result — only the shared catalog it is built from. In a multi-instance Cloud Run deployment, a process cache means per-instance staleness; that is acceptable at a 30-60 s TTL but must be a deliberate decision.
  - **Impact**: Removes 2 DB round-trips (one of them a full unfiltered table scan) per request from the highest-traffic uncached surface in the API, plus every checkout/subscription/loyalty/coach-agent call that resolves dishes.

- [ ] **OA-DEEP-1.4 Stop re-scanning the full rider table per dispatched order**
  - **Category**: Algorithmic / DB
  - **Severity**: High
  - **Evidence**: `dispatchOrderInner` runs `const allRiders = await db.select().from(ridersTable);` (`artifacts/api-server/src/lib/dispatch.ts:523`) — **no `WHERE` clause** — then filters to `status === "online"` in JS at line 527. The fetch is unconditional, not gated behind `if (!chosenRider)`. `dispatchReadyOrders` drives this from two sequential `for…of` loops over PAGE(=50)-sized batches (lines 770-781 STAT, 836-847 routine/urgent), so a sweep over P backlogged orders issues **P separate full-table reads**. `ridersTable` (`lib/db/src/schema/riders.ts`) has **zero indexes** — not even on `status` — so each is a true sequential scan.
  - **Fix**: Fetch and filter the rider pool **once per page/pass** in `dispatchReadyOrders` and pass it into `dispatchOrderInner` as an optional pre-fetched candidate list (`DispatchOptions` has no such field today); refresh every K assignments or when an assignment mutates a candidate's `activeOrderCount`. Minimum viable step: push the filter into SQL — `.where(eq(ridersTable.status, 'online'))` — and add `index("idx_riders_status_load").on(table.status, table.activeOrderCount)` (see `OA-MED-1.10`).
  - **Tradeoffs**: A shared pool is a **staleness/correctness tradeoff, and it interacts directly with `OA-DEEP-1.5`** — a pool cached across assignments makes the stale-load race *worse*, not better. Land the atomic-claim fix first, or land both together; do not take the pool caching alone.
  - **Impact**: O(orders × riders) round-trips → O(riders) per batch. On a surge of dozens of orders against a few hundred riders this removes tens of thousands of redundant row reads from the path the 5-minute STAT SLA depends on.

- [ ] **OA-DEEP-1.5 Make rider claim atomic instead of read-then-write**
  - **Category**: Concurrency
  - **Severity**: High
  - **Evidence**: Rider selection (`artifacts/api-server/src/lib/dispatch.ts:526-532`, weighted by `rider.activeOrderCount` at lines 197/204 with `DEFAULT_WEIGHTS.loadPerOrder = 2.5`) happens **before** the transaction, on a snapshot. The transaction takes `FOR UPDATE SKIP LOCKED` on the **order** row only (lines 573-580); nothing locks or reserves the chosen **rider**, and `activeOrderCount` is incremented only after commit (lines 608-615). `dispatchOrder` runs concurrently for different orders from three call sites: the BullMQ worker at `concurrency: ORDER_PIPELINE_CONCURRENCY` (default **4**, `queue.ts:230-234`), `POST /delivery/dispatch`, and the ops AI agent (`lib/ai/agents/ops.ts:482`).
  - **Failure scenario**: Four orders hit `ready` in the same second. All four `dispatchOrderInner` calls read rider R's `activeOrderCount` as 0 — none of the others has committed — and all four independently score R best. All four transactions succeed (different order rows, so no double-assignment error), and R ends up with 4 orders while equally-eligible riders idle. The `load * loadPerOrder` balancing term is silently defeated.
  - **Fix**: Either (a) `SELECT … FOR UPDATE` the candidate rider inside the same transaction that locks the order, re-validating it is still online and still best after acquiring the lock, falling back to next-best on conflict; or (b) make it a single atomic claim — `UPDATE riders SET active_order_count = active_order_count + 1 WHERE id = (SELECT id FROM riders WHERE status='online' ORDER BY <score> LIMIT 1 FOR UPDATE SKIP LOCKED) RETURNING id`.
  - **Tradeoffs**: (b) is cleaner but requires expressing the scoring heuristic in SQL — `scoreRiderForOrder` includes distance and rating terms that may not translate cleanly. (a) preserves the JS heuristic at the cost of holding a rider row lock for the transaction's duration; keep that transaction short. Either way this is a correctness-sensitive change to a money/ops path — cover it with a concurrent-dispatch test.
  - **Impact**: Restores intended load balancing during order surges — exactly when it matters most.

- [ ] **OA-DEEP-1.6 Fix the bulk CMS tools' guaranteed-timeout shape**
  - **Category**: Concurrency / Cost
  - **Severity**: High
  - **Evidence**: `bulk_regenerate_copy` (`artifacts/api-server/src/lib/ai/agents/cms.ts:803-842`) runs `for (const t of targets) { … await generateCopyForItem(…) … }` **serially for up to 25 items**, each with its own 12 s timeout (`lib/menuCopy.ts:334-370`). `bulk_generate_missing_heroes` does the same in `lib/menuAssets.ts:290-353` with **no per-call timeout at all**. Both execute as tool calls **inside a single `runAgent` call**, wrapped in one `AbortController` with `timeoutMs` defaulting to `DEFAULT_TIMEOUT_MS = 30_000` (`gateway.ts:106,265,335`), and `routes/cmsAgent.ts:94-101` never overrides it. 25 serial round-trips cannot fit in 30 s.
  - **Fix**: Route both tools through the existing `batchProcess` utility (`lib/integrations-gemini-ai/src/batch/utils.ts` — bounded concurrency + `p-retry` backoff/jitter) instead of a naive loop, **and** either raise `timeoutMs` for these specific agent calls or move bulk execution off the synchronous chat turn entirely, behind the SSE bulk-hero endpoint pattern the codebase already has.
  - **Tradeoffs**: Concurrency against Gemini raises 429 risk — keep the pool small (3-5) and rely on `batchProcess`'s backoff. Moving to async changes the operator UX from inline result to job-status, which is the correct shape for a 25-item batch but is a UI change.
  - **Impact**: Eliminates near-certain timeout failure on every non-trivial bulk run, along with the wasted Gemini spend and the orphaned partial writes (`applyCopyToItem` may have already committed for early items when the turn aborts).

- [ ] **OA-DEEP-1.7 Hoist the orders-window query out of the per-dish pricing loop**
  - **Category**: Algorithmic
  - **Severity**: High
  - **Evidence**: `buildPricingSuggestionsForRun` (`artifacts/api-server/src/lib/menuEngineering.ts:702-717`) loops `for (const s of stats) { … await buildDishSuggestions(…, run.windowStart, run.windowEnd, …) }`. Inside, **every call independently re-runs** `db.select(…).from(ordersTable).where(and(gte(…), lt(…), eq(orderKind,'meal')))` for the **same** window (lines 586-624), then scans `for (const o of orders) { o.items.some(…) }` — O(orders × items) repeated **per dish**. `aggregateDishStats` (lines 225-297) in the same file already demonstrates the correct one-pass shape.
  - **Fix**: Fetch the orders window once outside the loop (or reuse `aggregateDishStats`'s existing query), build a single `Map<slug, Map<"zone:daypart", count>>` in one pass, and have `buildDishSuggestions` read that pre-built slice map.
  - **Tradeoffs**: Holding the full window in memory — for a 180-day window this needs a sanity check on row count, and may warrant streaming or chunking if large.
  - **Impact**: O(dishes × orders × items) → O(orders × items + dishes). Removes a multiplicative factor equal to the entire dish count from both round-trips and in-memory scanning.

- [ ] **OA-DEEP-1.8 Fix the `/menu` server/client component boundary**
  - **Category**: Architectural — RSC boundary / bundle size
  - **Severity**: High
  - **Evidence**: `artifacts/storefront/components/menu/PersonalizedMenu.tsx` has `"use client"` at line 1 and statically imports `MenuGrid` at line 10, rendering it at line 112. `MenuGrid.tsx` in turn statically imports and renders `DishCard`. Under RSC semantics any module statically imported from a `"use client"` file compiles into the **client** bundle regardless of its own directives. Yet `MenuGrid.tsx`'s doc comment (lines 5-10) claims *"Server component: only DishCard's client primitives ship"* and `DishCard.tsx` (lines 14-16) claims *"STILL A SERVER COMPONENT — catalog data, the à-la-carte gate and the price stay server-side"*. **Both comments are false for the render path reached from `/menu`.** The full row markup for every dish — `RatingStars` star math, Astryx `<Text>`, `formatPaise`, `isAlaCarteEnabled` gating, the image box — ships and hydrates as client JS.   - **Fix**: Have the true Server Component (`app/menu/page.tsx`) pre-render the dish rows and pass them into `PersonalizedMenu` via `children`/named slots — the composition already used for `DishGallery`/`DishReviews` on the PDP. Keep only the diet chips and filter-trigger logic in the client boundary; toggle pre-rendered row visibility via CSS/data attributes keyed by dish id instead of re-mapping an array client-side. **Correct the two misleading comments** — they will otherwise re-mislead the next reader.
  - **Tradeoffs**: CSS-based filtering ships all rows' markup to the DOM even when filtered out, trading DOM size for JS size. That is the right trade at ~124 dishes, but pair it with `OA-MED-1.19` (pagination) so DOM size stays bounded.
  - **Impact**: Removes the entire catalog's non-interactive row markup and helper logic from the client bundle on the storefront's highest-traffic route, leaving only the diet-chip filter and the existing AddToCart islands.

- [ ] **OA-DEEP-1.9 Stop double-running the full test suite on every push to main**
  - **Category**: Infrastructure cost
  - **Severity**: High
  - **Evidence**: `.github/workflows/deploy.yml` has **no path filter** on its push trigger (lines 29-30) and its `gate` job is conditioned only on `if: github.event_name == 'push'` (line 96) — not on the `changes` job's outputs. The 29-file integration list (lines 163-197) is a **verbatim subset** of `verify.yml`'s money-integration list (lines 300-330); the unit list (lines 140-151) duplicates `verify.yml`'s (lines 83-95) bar one file. `verify.yml` **also** triggers on `push: branches: [main]` with paths `artifacts/**`, `lib/**` (lines 29-34) — the same event, same commit. `gate`'s justifying comment ("PR CI tests the branch tip; the gate tests what is actually deploying", lines 19-23) therefore does not hold: `verify.yml` already re-tests the merge commit.
  - **Fix**: Either (a) apply the same path filter to `gate` via the existing `changes` job's `dorny/paths-filter` outputs, so it skips irrelevant pushes; or (b) remove the duplication structurally — gate the deploy on `verify.yml`'s conclusion for that exact sha via `workflow_run`.

### OA-DEEP-1.1 — Shape of the hardened AE path

```ts
// 1. Persist FIRST — the medico-legal record must survive any downstream failure.
await this.dbGateway.saveDossier(dossier);

// 2. Fire independent actions concurrently, each individually bounded.
//    PagerDuty must not gate the batch lock or the patient warning.
const [paged, locked, replied] = await Promise.allSettled([
  withTimeoutAndRetry(() => this.pagerDutyGateway.triggerIncident(...)),
  activeOrder?.lot_number
    ? withTimeoutAndRetry(() => this.kitchenErpGateway.lockBatchLot(...))
    : Promise.resolve(null),
  withTimeoutAndRetry(() => this.whatsAppGateway.sendTextMessage(senderPhone, emergencyReply)),
]);

dossier.actions_triggered = {
  pagerduty_paged: paged.status === "fulfilled",
  kitchen_batch_locked: locked.status === "fulfilled" ? activeOrder?.lot_number : undefined,
  patient_auto_reply_sent: replied.status === "fulfilled",
};
```
